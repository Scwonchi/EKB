# Протокол устройств: как написать свой сервер

Документ для тех, кто пишет сервер, принимающий данные от устройств с радаром.
Схемы сообщений — `proto/telemetry/v1/telemetry.proto` и `proto/telemetry/v1/synack.proto`.
Формат кадров, рукопожатие Syn/Ack и ограничения значений совпадают с сервером команды
**iot-go** (Go; его документы — `docs/iot-go/`): прошивки работают и с ним,
и с эталонным `server/server.py` (Python). Сервер, который выполняет этот документ и отдаёт
HTTP API из `api/openapi.yaml`, полностью заменяет эталонный.

## Коротко

- Устройство само подключается к серверу по TCP. Первым кадром — `telemetry.v1.Syn`:
  MAC устройства (6 байт) и оборудование на борту (камера и её адрес).
- Сервер отвечает одним кадром `telemetry.v1.Ack`: `code = 0` — принят, иначе отказ
  и закрытие подключения.
- Дальше устройство около **5 раз в секунду** присылает **полный снимок** состояния —
  `telemetry.v1.Telemetry`. Сервер больше ничего не отправляет.
- Каждый снимок описывает состояние целиком. Предыдущие снимки для понимания
  текущего не нужны, потерянный снимок ничего не ломает.
- Устройство узнаётся по **MAC из Syn**; свой идентификатор для API назначает сервер.

## Участники

```
ESP32 с радаром ──TCP──────────────────────────────────────────> сервер (порт 9000)
разведчик ──Wi-Fi──> ретранслятор на Mavic ──Wi-Fi роутера──TCP──> сервер (байты в обе стороны)
ESP32 с радаром ──TCP──> ESP-шлюз ──USB (кадры шлюза)──> server.py --serial
```

- **Устройство** — ESP32 с радаром LD2450, GPS и компасом. Подключается к серверу
  само и переподключается при обрыве.
- **Шлюз** (необязательно) — ESP32, которая раздаёт Wi-Fi устройствам и пересылает
  их TCP-потоки на ПК по USB. Protobuf не разбирает.
- **Сервер** — принимает снимки и отдаёт данные клиентам.

Сервер должен поддерживать хотя бы один способ подключения: TCP или USB-шлюз.

## Транспорт TCP

- Сервер слушает TCP-порт **9000** (номер задаётся в прошивке, `SERVER_PORT`).
- Одно устройство — одно TCP-подключение. Устройство — клиент.
- От устройства идут кадры:

```
[длина тела — 4 байта, uint32 BigEndian][сообщение telemetry.v1.Telemetry]
```

  Длина — число байт protobuf-тела без заголовка. Кадры идут подряд, без разделителей.
- Снимок с 6 целями занимает до **279 байт** тела. iot-go принимает тела до **64 КиБ**,
  кадр длиннее — признак сбоя, подключение закрывается.
- Сервер пишет в подключение только один кадр — `Ack` в ответ на `Syn`. Если после него
  что-то придёт, устройство это прочтёт и выбросит.

Проверочный вектор (из документации iot-go): `Telemetry{uptime_s: 1}` →

```
00 00 00 02 | 10 01
длина = 2     uptime_s = 1
```

Пустой снимок (все поля по умолчанию) — кадр `00 00 00 00`, он допустим.

Векторы рукопожатия: `Syn{mac: 02:11:22:33:44:55}` → `00 00 00 08 0A 06 02 11 22 33 44 55`,
`Ack{code: 0}` → `00 00 00 00` (пустое тело), `Ack{code: 1}` → `00 00 00 02 08 01`.
Все векторы и полный пример снимка из документации iot-go проверяет `tools/codec_test.cpp`.
В полном примере iot-go (`iot-device-client-tutorial.md`) пропущен один байт `FF`: у
`rssi_dbm = -55` varint занимает 10 байт (`C9`, восемь `FF`, `01`), а там семь `FF` —
92 байта тела при заголовке `5D` = 93. Кодек прошивки и Python protobuf дают 93 байта.

## Рукопожатие Syn/Ack

```
устройство                                 сервер
   | --- [len] Syn{mac, onboards} ----------> |  MAC — 6 сырых байт, постоянный
   | <-- [len] Ack{code} -------------------- |  0 — принят; иначе отказ, закрытие
   | --- [len] Telemetry -------------------> |  каждые 200 мс, до разрыва
```

- `Syn` — при **каждом** новом подключении: MAC (`WiFi.macAddress`, STA) и полный список
  оборудования. Разведчик с камерой пишет `camera` → адрес потока MJPEG:
  через ретранслятор — `http://<ретранслятор в сети роутера>:8000/<номер>/stream`, напрямую —
  `http://<разведчик>:81/stream`; `camera_page` — страница камеры (`…:8000/<номер>/` или
  `http://<разведчик>/`). Адрес и свой номер разведчик узнаёт у ретранслятора
  (`http://192.168.5.1:8000/ip` → «192.168.1.40 2»): у каждого разведчика за одним
  ретранслятором своя ссылка. Без камеры список пуст.
- Отказ (`code ≠ 0`) — устройство закрывает подключение и повторяет через 10 с.
- Режимы в прошивке (`SERVER_HANDSHAKE`, `TelemetryLink::Config.handshake`):

| Режим | Нет Ack за 3 с | Для какого сервера |
|---|---|---|
| `HS_AUTO` (по умолчанию) | соединение живо — снимки идут дальше в нём же | и старый iot-go (без Syn/Ack), и новый |
| `HS_STRICT` | закрыть, переподключиться | только новый — строго по документу iot-go |
| `HS_OFF` | Syn не отправляется | только старый |

  `HS_AUTO` работает со старым iot-go потому, что его разбор принимает `Syn` как пустой
  снимок (у поля 1 другой тип — protobuf считает его неизвестным полем); проверено кодом
  iot-go — `readFrame`, `proto.Unmarshal`, `Validate`.
- Через ретранслятор и запасную сеть рукопожатие идёт так же: ретранслятор пересылает
  байты в обе стороны. Все разведчики за ретранслятором приходят к серверу с одного адреса,
  различаются по MAC.
## Ограничения значений

Сервер проверяет снимок и **закрывает подключение на первом неверном**
(iot-go — `domain.Telemetry.Validate`, `server.py` — `validate`):

- числа конечные — никаких NaN и бесконечностей;
- `person_probability`, `hit_ratio` — от 0 до 1;
- `position`: широта −90…90, долгота −180…180;
- `hdop`, `distance_m`, `speed_mps` — не отрицательные;
- `heading_deg` — в диапазоне [0, 360), ровно 360 — ошибка;
- `heading_valid = true` только вместе с `heading_deg`;
- целей не больше 6.

Прошивки перед отправкой приводят снимок к этим правилам (`telemetry::sanitize`
в `telemetry_codec.h`): курс 360° превращается в 0°, NaN-координаты — в «нет фиксации»,
отрицательная скорость — в модуль, цель с NaN-дистанцией выбрасывается. Иначе одна
неверная величина от датчика давала бы бесконечные переподключения. Сколько снимков
пришлось исправить, показывает `telem.fixedCount`.

## Идентификатор устройства

Устройство узнаётся по **MAC из Syn**: он один и тот же после перезагрузки и
переподключения. Идентификатор для API сервер назначает сам (новый iot-go — свой
постоянный для MAC; эталонный сервер — сам MAC, `02:11:22:33:44:55`).

Новое подключение с тем же MAC — переподключение того же устройства: старое закройте.

Старые прошивки без Syn: идентификатор — IP-адрес подключения (эталонный сервер),
у старого iot-go — новый UUID на каждое подключение.

## Снимок Telemetry: как читать поля

| Поле | Смысл и правила |
|---|---|
| `firmware_version`, `uptime_s` | версия прошивки и время с включения, с |
| `radar_ok` | радар присылает данные; `false` — цели в снимке недостоверны |
| `detection_class`, `person_probability` | итог по самой надёжной подтверждённой цели или `EMPTY` |
| `position` | координаты; **поле отсутствует** — нет фиксации GPS (проверяйте наличие поля, а не нули). У разведчика в помещении — точка старта, заданная оператором, плюс одометрия (`satellites = 0`): из них сервер рисует трек |
| `satellites` | спутников; есть и без фиксации |
| `hdop` | `optional`: нет поля — точность неизвестна |
| `heading_valid`, `heading_deg` | курс радара от истинного севера; использовать, **только если** `heading_valid = true` и поле `heading_deg` присутствует |
| `rssi_dbm` | сила сигнала Wi-Fi |
| `target_count` | подтверждённых людей |
| `tracks` | все цели радара, до 6; пустой список — целей нет |
| `learning_background`, `background_cells` | устройство запоминает фон (целей в это время нет); сколько клеток помечено как фон |
| `alarm_active` | на устройстве активна тревога |

Цель `Track`: `id` (живёт, пока цель видна), `distance_m`, `angle_deg` (от оси
радара, плюс по часовой, −60…+60), `speed_mps`, `confirmed` (это человек),
`detection_class` (для подтверждённых), `hit_ratio` (доля кадров, где цель видна).

Азимут на цель = `heading_deg + angle_deg` (по модулю 360), если курс достоверен.

## Тревоги

Отдельного сообщения о тревоге нет — есть состояние `alarm_active` в каждом снимке.
Сервер выводит события сам:

- `alarm_active`: `false` → `true` (или первый снимок подключения с `true`, если у
  устройства не было активной тревоги) — **новая тревога**;
- `true` → `false` — **тревога снята**.

Устройство `ld2450_search` держит `alarm_active = true`, пока видит подтверждённого
человека, и ещё 5 с после того, как перестало его видеть (разведчик `rescue_scout` —
пока на карте обнаружения есть люди). При снимках 5 раз в секунду это не меньше
25 снимков подряд, поэтому сервер тревогу не пропустит. Так же сказано в комментарии
контракта: это состояние, а не гарантированное событие. Тревога короче периода
снимков теоретически может пройти незамеченной.

Данные для тревоги берите из снимка, в котором она началась: самая надёжная
подтверждённая цель (наибольший `hit_ratio`) даёт дистанцию и угол; курс и
координаты устройства — точку человека.

Обрыв связи во время тревоги: эталонный сервер оставляет тревогу активной до
следующего снимка этого устройства. Если в нём `alarm_active = false`, тревога
снимается.

## Сроки

- Устройство шлёт снимок каждые 200 мс (прошивка `ld2410c_nn` — раз в секунду).
- Нет полного кадра дольше `server_tcp.read_timeout` — iot-go закрывает подключение. В коде
  iot-go (`internal/transport/iot/server.go`) по умолчанию **30 с**, в его документации — 5 с;
  устройства шлют снимок каждые 200 мс, поэтому подходит любое из значений. Эталонный сервер — 5 с.
- Ack iot-go отправляет после регистрации устройства (на неё отводится до того же `read_timeout`).
  Устройство ждёт Ack **3 с** в режиме `HS_AUTO` (дальше всё равно шлёт снимки — сервер прочтёт их
  после Ack) и **10 с** в `HS_STRICT`.
- Старый протокол (`HS_OFF`, сразу `Telemetry`) новый iot-go не принимает: первый кадр он читает
  как `Syn`, MAC в нём пустой — `Ack{code: 1}` и закрытие.
- Переподключение с тем же MAC: iot-go выдаёт тот же ID устройства и закрывает старое подключение,
  если оно ещё висит (например, обрыв Wi-Fi, а сервер ещё не заметил).
- Потерю связи устройство замечает по ошибке записи в TCP и переподключается
  с паузами 1, 2, 4, 8, затем 10 с.

## Транспорт через USB-шлюз

Сервер открывает последовательный порт шлюза (921600 бод, 8N1; для встроенного USB
ESP32 скорость не важна). DTR и RTS лучше держать в 0: иначе плата с USB-UART мостом
может перезагрузиться при открытии порта. В обе стороны идут кадры:

```
A5 | тип | клиент | длина (2 байта, младший первым) | данные | CRC-8
```

| Тип | Направление | Данные |
|---|---|---|
| `01` CONNECT | шлюз → сервер | IPv4 устройства, 4 байта — это и есть идентификатор у эталонного сервера |
| `02` DATA | шлюз → сервер | байты TCP-потока этого клиента |
| `03` DISCONNECT | в обе стороны | нет; от сервера — «закрой этого клиента» |
| `04` STATUS | шлюз → сервер, раз в 2 с | клиентов (1 байт), время работы в с (4 байта, LE), станций Wi-Fi (1 байт) |
| `05` RESET | сервер → шлюз | нет; закрыть всех клиентов |

- `клиент` — номер TCP-подключения у шлюза (1–255), для STATUS и RESET — 0.
- Длина данных — до 1024 байт.
- CRC-8: полином 0x07, начальное значение 0, без отражения, без финального XOR;
  считается по байтам от «тип» до последнего байта данных. Проверочное значение:
  кадр `A5 02 07 05 00 01 02 03 A5 FA` имеет CRC `63`.
- Кадр с неверной CRC пропустите и ищите следующий байт `A5`: при запуске шлюза
  в порт может попасть текст загрузчика ESP32.
- **DATA не совпадает с границами снимков.** Шлюз пересылает куски TCP-потока
  как есть, поэтому для каждого клиента соберите байты в отдельный поток и уже
  из него выделяйте кадры `[4 байта длины][Telemetry]` — так же, как из TCP.
- При открытии порта отправьте RESET: устройства переподключатся, и сервер начнёт
  с чистого состояния.
- Ответ сервера (`Ack`) через USB-шлюз до устройства не доходит. Прошивка в режиме
  `HS_AUTO` через 3 с без Ack продолжает работать; `HS_STRICT` через шлюз не работает.
  Новый iot-go USB-шлюз не поддерживает.
- Если `станций Wi-Fi` больше, чем клиентов, значит, какое-то устройство вошло в сеть
  шлюза, но не подключилось к серверу. Чаще всего в его прошивке неверный `SERVER_HOST`.

### Шлюз и сервер без поддержки USB (iot-go)

iot-go принимает только TCP. Для него на ПК со шлюзом запускается мост:

```sh
python server/gateway_bridge.py --serial /dev/ttyACM0 --server 127.0.0.1:9000
```

Мост для каждого устройства у шлюза открывает своё TCP-подключение к серверу и
пересылает байты как есть. Сервер видит все устройства с адреса ПК.

## Код для своего языка

Схема — `proto/telemetry/v1/telemetry.proto`. Код генерирует easyp, все генераторы
перечислены в `easyp.yaml`. Например, для Go добавьте плагин и выполните `easyp generate`:

```yaml
    - name: go                  # нужен protoc-gen-go в PATH
      out: server-go/gen
      opts:
        paths: source_relative
```

Без easyp подойдёт обычный `protoc` (версии 3.15 и новее — из-за `optional`).

Изменения схемы — по правилам protobuf: новые поля с новыми номерами; номера и типы
существующих не менять; удалённые — в `reserved`. Перед изменением —
`easyp breaking --against main`.

## Как проверить свой сервер

1. Запустите свой сервер на порту 9000.
2. `python tools/sim_device.py --count 2` — два имитатора устройств (MAC 02:51:4d:00:00:01,
   …:02) делают Syn/Ack и шлют снимки по сценарию: человек идёт, второй сидит, ложные
   точки, тревоги и отбои. `--handshake strict` — строго по протоколу, `off` — старый протокол.
3. `tools/fake_device.cpp` — то же на C++ с кодом nanopb из прошивки: короткий сценарий
   с одной тревогой и отбоем (`./fake_device 127.0.0.1 9000 strict`).
4. Отказ: `python server/server.py --reject 02:51:4d:00:00:02` — второму имитатору сервер
   отвечает `Ack{code: 1}`, он повторяет через 10 с. `--require-syn` — как новый iot-go:
   первым кадром только Syn.
5. `python tools/check_api.py http://localhost:8080` — проверка HTTP API (`docs/web-api.md`).
6. `tools/codec_test.cpp` — проверочные векторы кадров.
