# Туториал: клиент IoT-устройства

Этот документ описывает клиентскую сторону протокола сервиса. Его можно передать
ИИ-ассистенту или команде, реализующей прошивку устройства. Основной контракт —
[`device-protocol.md`](device-protocol.md); protobuf-схемы —
[`proto/telemetry/v1/synack.proto`](../proto/telemetry/v1/synack.proto) и
[`proto/telemetry/v1/telemetry.proto`](../proto/telemetry/v1/telemetry.proto).

## Краткое ТЗ для реализации

Реализуйте клиент, который:

1. Подключается по TCP и первым кадром отправляет `telemetry.v1.Syn` с MAC
   устройства и актуальным списком оборудования `onboards`.
2. Читает кадр `telemetry.v1.Ack`: при `code=0` продолжает, при `code=1`
   закрывает соединение и не отправляет телеметрию.
3. После успешного ACK периодически собирает **полный текущий снимок**.
4. Кодирует снимок как `telemetry.v1.Telemetry` в Protocol Buffers и передаёт
   кадром: 4-байтовая длина в BigEndian, затем protobuf-тело.
5. При ошибке записи или разрыве соединения закрывает сокет, повторно
   подключается и начинает новый handshake с `Syn`.

Не добавляйте в `Telemetry` `device_id`, `seq` или `boot_id`: их нет в контракте.
Старый режим, в котором первым кадром отправляется `Telemetry`, не поддерживается.

### Шаблон задания для ИИ-ассистента

Передайте ассистенту этот документ и актуальный файл `.proto`, затем заполните
параметры в шаблоне:

> Реализуй TCP-клиент IoT-устройства на **`<язык/платформа>`** для сервиса,
> описанного в приложенном руководстве. При каждом соединении первым кадром
> отправляй `telemetry.v1.Syn` с MAC (6 raw bytes) и текущим полным списком
> `onboards`, затем читай `telemetry.v1.Ack`: `0` означает продолжить, `1` —
> закрыть соединение. Только после `Ack{code: 0}` отправляй периодические полные
> `telemetry.v1.Telemetry`. Все кадры имеют 4-байтовый BigEndian-префикс длины.
> Соблюдай ограничения полей и optional-presence, обработай частичную запись,
> чтение полного кадра, разрыв соединения и повторное подключение без очереди
> устаревшей телеметрии. Не отправляй старый формат, где первым кадром идёт
> Telemetry. Не выдумывай отсутствующие поля или семантику; вопросы и
> предположения перечисли отдельно.

> Текущий backend пока не реализует Syn/Ack; проверять handshake можно после
> развёртывания серверной поддержки.

## 1. Параметры подключения и поведение сервера

- Протокол: TCP, без TLS на стороне текущего сервиса.
- Порт по умолчанию: `9000` (может быть изменён конфигурацией сервера).
- Один TCP-сеанс начинается с `Syn`, затем сервер отвечает одним `Ack`; после
  успешного ACK клиент может отправлять последовательные кадры `Telemetry`.
- По умолчанию сервис закрывает соединение, если не получает следующий полный
  кадр в течение 5 секунд (включая ожидание и чтение заголовка и тела). Настройка —
  `server_tcp.read_timeout` / `TCP_READ_TIMEOUT`. Клиенту следует отправлять снимок
  чаще; рекомендуемый начальный интервал — **1 секунда**.
- Максимальный размер protobuf-тела одного кадра по умолчанию — **65 536 байт**;
  настройка — `server_tcp.max_message_size` / `TCP_MAX_MESSAGE_SIZE`.
- Устройство передаёт стабильный MAC в `Syn`; backend назначает стабильный API ID
  тому же MAC при reconnect. Устройство не отправляет этот ID.
- `Ack.code=0` разрешает telemetry; `Ack.code=1` означает отказ и закрытие TCP.
  Некорректный `Syn` может завершиться закрытием без ACK.
- После ACK сервер не подтверждает отдельные telemetry-кадры и не отправляет
  команды. При разрыве нужно подключиться заново и повторить Syn.

Идентификатор виден Web-клиентам через список активных устройств и URL
WebSocket-подписки; IoT-клиенту для отправки телеметрии он не нужен.

## 2. Формат TCP-кадра

Каждый protobuf-пакет оборачивается следующим образом:

| Смещение | Размер | Формат | Значение |
|---:|---:|---|---|
| 0 | 4 байта | `uint32`, BigEndian | Размер protobuf-тела в байтах, без заголовка |
| 4 | N байт | Protobuf | `Syn`, `Ack` или `Telemetry` — по направлению и состоянию сессии |

Кадры идут подряд. Разделители, переводы строк и дополнительные заголовки не
передаются. Размер измеряется **после protobuf-кодирования**.

### Проверочный вектор фрейминга

Для минимального protobuf-сообщения `Telemetry{uptime_s: 1}` тело равно `10 01`.
Полный TCP-кадр:

```text
00 00 00 02 10 01
```

### Полный пример снимка и кадра

Ниже пример `Telemetry`, где заданы все поля верхнего уровня, координаты,
optional-поля и одна цель с заполненными полями `Track`:

```text
firmware_version: 3
uptime_s: 42
radar_ok: true
detection_class: DETECTION_CLASS_MOVING
person_probability: 0.88
position { lat: 56.8389 lon: 60.6057 }
satellites: 10
hdop: 0.9
heading_valid: true
heading_deg: 42
rssi_dbm: -55
target_count: 1
tracks {
  id: 1 distance_m: 4.5 angle_deg: -12 speed_mps: 0.7
  confirmed: true detection_class: DETECTION_CLASS_MOVING hit_ratio: 0.95
}
learning_background: false
background_cells: 24
alarm_active: true
```

После сериализации **текущей** схемой кадр будет:

```text
00 00 00 5D
08 03 10 2A 18 01 20 02 2D AE 47 61 3F 32 12 09 A5 4E 40 13 61 6B 4C 40
11 F6 97 DD 93 87 4D 4E 40 38 0A 45 66 66 66 3F 48 01 55 00 00 28 42 58 C9
FF FF FF FF FF FF FF 01 60 01 6A 1A 08 01 15 00 00 90 40 1D 00 00 40 C1 25
33 33 33 3F 28 01 30 02 3D 33 33 73 3F 78 18 80 01 01
```

Заголовок `00 00 00 5D` означает, что protobuf-тело занимает `0x5D = 93` байта;
кадр целиком — 97 байт. Поля proto3 со значением по умолчанию всё равно заданы
в логическом снимке, но обычно не кодируются в binary: в этом примере
`learning_background: false` не имеет отдельного участка байтов. Декодер
восстанавливает его как `false`.

Отрицательный `int32 rssi_dbm=-55` занимает десять байт varint — это нормальное
protobuf-кодирование `int32`, не ошибка framing.

В proto3 сообщение, у которого все поля имеют значения по умолчанию, может
кодироваться пустым protobuf-телом. Такой кадр имеет длину `00 00 00 00` и
допустим форматом protobuf; практически устройство должно заполнять снимок
доступными измерениями.

### Запись кадра

Вызов `write()`/`send()` может записать меньше байтов, чем запрошено. Для
заголовка и тела используйте цикл `write_all`: продолжайте запись с оставшейся
части буфера, пока весь буфер не передан или не произошла ошибка.

Псевдокод:

```text
message = collect_current_snapshot()
body = protobuf_encode(message)
header = uint32_big_endian(length(body))

write_all(socket, header)
write_all(socket, body)
```

Не объединяйте кадры в свой пакет с дополнительным форматом и не отправляйте
protobuf-тело без четырёхбайтового заголовка.

## 3. Protobuf-контракт

После успешного handshake каждое тело кадра от устройства содержит одно сообщение:

```protobuf
telemetry.v1.Telemetry
```

Это **полный снимок**, а не delta. Каждый отправленный пакет должен описывать
всё текущее состояние. В частности, пустой `tracks` означает, что целей сейчас
нет; отсутствие `position` означает отсутствие GPS-фиксации. Сервер не хранит
состояния датчиков на стороне устройства между пакетами.

### `Telemetry`

| Поле | Тип | Значение и ограничения |
|---|---|---|
| `firmware_version` | `uint32` | Версия прошивки. Способ кодирования версии задаёт производитель устройства; передавайте его одинаково во всех сообщениях одной версии. |
| `uptime_s` | `uint32` | Время с момента включения устройства, секунды. После перезагрузки может начаться с нуля. |
| `radar_ok` | `bool` | `true`, если радар работает и передаёт данные. |
| `detection_class` | `DetectionClass` | Последний общий класс результата анализа радара. |
| `person_probability` | `float` | Вероятность присутствия человека, конечное число от `0` до `1`. |
| `position` | `GeoPoint` | Координаты устройства WGS-84. Не задавайте поле, если GPS-фиксации нет. Координата `(0, 0)` — допустимое значение и не означает отсутствие фиксации. |
| `satellites` | `uint32` | Число спутников, используемых GPS-приёмником; `0`, если значение недоступно. |
| `hdop` | `optional float` | Неотрицательный конечный HDOP. Не задавайте optional-поле, если значение неизвестно; значение `0` отличается от отсутствующего поля. |
| `heading_valid` | `bool` | `true`, если курс достоверен. При `true` поле `heading_deg` обязательно. |
| `heading_deg` | `optional float` | Азимут радара от истинного севера в диапазоне `[0, 360)`. При недостоверном/неизвестном курсе задайте `heading_valid=false`; значение не используется. |
| `rssi_dbm` | `int32` | Уровень Wi-Fi-сигнала в dBm. |
| `target_count` | `uint32` | Число подтверждённых людей в зоне радара. Это не обязательно равно количеству всех треков. |
| `tracks` | `repeated Track` | Полный список текущих целей, от `0` до `6` элементов. |
| `learning_background` | `bool` | `true`, пока радар запоминает фон. |
| `background_cells` | `uint32` | Число ячеек, помеченных радаром как фон. |
| `alarm_active` | `bool` | Состояние тревоги в момент снимка. Это не гарантированное событие: короткая тревога между периодическими отправками может быть пропущена. |

Скалярные поля proto3, равные нулю/`false`, обычно не занимают места в protobuf-
пакете. Это нормально: сервер восстановит значения по умолчанию. Для `position`
и полей `optional` сохраняйте смысл наличия поля.

### `DetectionClass`

Передавайте следующие числовые значения enum из схемы:

| Значение | Имя | Смысл |
|---:|---|---|
| 0 | `DETECTION_CLASS_UNSPECIFIED` | Значение неизвестно или не задано |
| 1 | `DETECTION_CLASS_EMPTY` | Целей не обнаружено |
| 2 | `DETECTION_CLASS_MOVING` | Обнаружен движущийся человек |
| 3 | `DETECTION_CLASS_STATIONARY` | Обнаружен неподвижный человек, например по дыханию |
| 4 | `DETECTION_CLASS_INTERFERENCE` | Помеха: например, вентилятор, шторы или животное |

При отсутствии классификации используйте значение `0`, а не случайное число.
Неизвестные значения enum не разрывают TCP-соединение и сохраняются во внутренней
модели сервера; WebSocket-представление показывает неизвестный класс как
`unspecified`.

### `GeoPoint`

| Поле | Тип | Ограничение |
|---|---|---|
| `lat` | `double` | Широта в градусах, конечное число `[-90, 90]` |
| `lon` | `double` | Долгота в градусах, конечное число `[-180, 180]` |

### `Track`

| Поле | Тип | Значение и ограничения |
|---|---|---|
| `id` | `uint32` | Локальный ID трека; сохраняется, пока цель видна. Это не ID устройства. |
| `distance_m` | `float` | Расстояние от радара, метры; конечное число `>= 0`. |
| `angle_deg` | `float` | Угол от оси радара, градусы; положительное направление — по часовой стрелке. Значение должно быть конечным; диапазон зависит от радара и отдельно сервером не ограничивается. |
| `speed_mps` | `float` | Модуль скорости, м/с; конечное число `>= 0`. |
| `confirmed` | `bool` | Подтверждено ли, что цель — человек. |
| `detection_class` | `DetectionClass` | Класс цели; имеет смысл для подтверждённых целей. |
| `hit_ratio` | `float` | Доля кадров, в которых цель видна, конечное число `[0, 1]`. |

Сервер отклонит снимок, если в нём больше шести треков, числовые значения не
конечны (`NaN`/`Infinity`), вероятности/доли выходят за `0..1`, координаты вне
диапазона, дистанция/скорость/HDOP отрицательны или достоверный курс передан без
`heading_deg`. После такого пакета TCP-соединение закрывается.

## 4. Рекомендуемый цикл клиента

Алгоритм прошивки может оставаться простым:

```text
loop:
    socket = tcp_connect(server_host, server_port)
    if connect failed:
        wait короткую паузу (желательно с ограниченным backoff)
        continue

    send_frame(socket, protobuf_encode(Syn(mac, current_onboards)))
    ack = receive_one_frame_with_timeout(socket)
    if ack cannot be decoded or ack.code != 0:
        close(socket)
        wait with bounded backoff
        continue

    while socket is connected:
        snapshot = read_current_sensor_state()
        validate snapshot locally
        body = protobuf_encode(Telemetry(snapshot))
        write_all(socket, uint32_big_endian(length(body)))
        write_all(socket, body)
        sleep_until_next_period()

    close(socket)
    discard queued old snapshots
    reconnect and repeat the Syn/Ack handshake
```

Дополнительные рекомендации:

- При reconnect отправляйте свежий снимок, а не накопленную историю. Протокол
  предназначен для передачи текущего состояния.
- Не ждите ACK на каждый telemetry-кадр: сервер отвечает только один раз на Syn.
- Если запись не завершилась, считать кадр отправленным нельзя. Закройте
  соединение и после reconnect отправьте новый снимок.
- Не отправляйте `NaN`/`Infinity` в `float`/`double`, даже если используемая
  protobuf-библиотека позволяет их сериализовать.
- Используйте protobuf-код, сгенерированный из общей `.proto`-схемы. Перед
  сериализацией ограничивайте `Telemetry.tracks` шестью элементами; сервер также
  проверяет этот лимит.
- Не включайте TLS самостоятельно, если серверная сторона не настроена на TLS.
  Текущий TCP endpoint принимает обычный TCP; для недоверенной сети потребуются
  VPN/TLS-терминация и согласованная конфигурация сервера.

## 5. Сборка и проверка

1. Получите эту `.proto`-схему из репозитория сервиса и сгенерируйте код для
   выбранного языка/платформы. Не переписывайте номера protobuf-полей вручную.
2. Соберите пакет `Telemetry` из доступных измерений; отсутствующие значения
   GPS представляйте отсутствием `position`/`hdop`, а не фиктивными координатами.
3. Проверьте локальную protobuf-сериализацию и фрейминг на векторе
   `Telemetry{uptime_s: 1}` → `00 00 00 02 10 01`.
4. Запустите сервер и имитатор из корня backend-репозитория:

   ```sh
   go run ./cmd/server
   go run ./cmd/iot -server 127.0.0.1:9000 -interval 1s
   ```

   Команды запускаются в разных терминалах. Имитатор показывает пример
   периодического соединения и генерации кадров.

5. После реализации handshake проверьте `GET http://127.0.0.1:8080/api/v1/devices`:
   устройство должно иметь стабильный API ID и список `onboards`. WebSocket-
   подписка на телеметрию выполняется по `/api/v1/devices/{id}`.

## 6. Чек-лист совместимости

- [ ] Клиент использует `telemetry.v1.Telemetry` из актуальной схемы.
- [ ] Один TCP-кадр содержит ровно один protobuf-снимок с 4-байтовой длиной
      BigEndian.
- [ ] Реализована полная запись буферов при частичном `write()`.
- [ ] Первым кадром каждого соединения отправляется Syn с MAC и `onboards`.
- [ ] Клиент читает Ack; telemetry отправляется только после `code=0`.
- [ ] При `code=1` клиент закрывает соединение и не отправляет telemetry.
- [ ] Каждый пакет содержит полный актуальный список `tracks` (не более 6).
- [ ] Отсутствующие GPS/optional значения не заменяются фиктивной координатой.
- [ ] `heading_valid=true` сопровождается `heading_deg` в `[0, 360)`.
- [ ] После разрыва клиент переподключается и повторяет Syn/Ack handshake,
      затем отправляет свежий снимок без очереди старых данных.
- [ ] Клиент не рассчитывает на гарантированную доставку переходов тревоги.

## 7. Важные границы протокола

- Handshake подтверждает регистрацию, но ACK не подтверждает отдельные
  telemetry-снимки; командного канала нет.
- MAC идентифицирует устройство, но не аутентифицирует его.
- `alarm_active` — выборка состояния, а не очередь событий.
- Серверный TCP-трафик сейчас не защищён TLS и не аутентифицирует устройство.
- WebSocket — отдельный канал для веб-клиентов; IoT-устройству подключаться к
  нему или формировать WebSocket JSON не нужно.
