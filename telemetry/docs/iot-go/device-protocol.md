# Протокол IoT-устройств

Документ описывает целевой алгоритм подключения устройства к backend и передачи
телеметрии. Контракты находятся в:

- [`proto/telemetry/v1/synack.proto`](../proto/telemetry/v1/synack.proto) — `Syn`/`Ack`;
- [`proto/telemetry/v1/telemetry.proto`](../proto/telemetry/v1/telemetry.proto) — `Telemetry`.

## Статус реализации

**Протокол Syn/Ack пока не реализован TCP-сервером.** Текущий backend ожидает
`Telemetry` сразу после TCP-подключения, не отправляет ACK и назначает UUID
каждому соединению. Прошивку на новый алгоритм переводите только после того,
как поддержка handshake будет добавлена и развёрнута на сервере.

## Кратко

1. Устройство подключается к серверу по TCP.
2. Первым кадром устройство отправляет полный `Syn`: MAC и список оборудования.
3. Сервер проверяет `Syn`, регистрирует устройство и отвечает кадром `Ack`.
4. При `Ack.code == 0` устройство начинает периодически отправлять полные
   снимки `telemetry.v1.Telemetry`.
5. При ненулевом `Ack.code` сервер закрывает соединение; telemetry в этой сессии
   отправлять нельзя.

После успешного `Ack` протокол снова односторонний: сервер не подтверждает
каждый снимок и не отправляет команды.

## TCP-транспорт

Каждый кадр в обе стороны имеет одинаковую оболочку:

```text
[4 байта длины uint32 BigEndian][N байт protobuf-сообщения]
```

- Длина — число байтов protobuf-тела, без четырёхбайтового заголовка.
- Кадры передаются подряд, без разделителей.
- Вызов `write`/`send` может записать только часть буфера: реализуйте
  `write_all` для заголовка и тела.
- Порт по умолчанию в текущей конфигурации backend — `9000`; он настраивается
  в `configs/config.yaml`.
- Лимит protobuf-тела по умолчанию — `65 536` байт; серверная настройка —
  `server_tcp.max_message_size` / `TCP_MAX_MESSAGE_SIZE`.
- Таймаут чтения полного кадра — `5s` по умолчанию; серверная настройка —
  `server_tcp.read_timeout` / `TCP_READ_TIMEOUT`.

Это **не** protobuf-delimited формат: длина кодируется ровно четырьмя байтами
BigEndian, не varint.

## Первый кадр: `Syn`

При каждом новом TCP-подключении первым кадром обязательно отправляется
`telemetry.v1.Syn`.

### Идентичность устройства

`mac` — ровно 6 сырых байтов MAC/EUI-48 в стандартном порядке октетов. Не
передавайте ASCII-строку вроде `"02:11:22:33:44:55"` и не добавляйте завершающий
нулевой байт. MAC должен быть стабильным между перезагрузками и reconnect.

Устройство не генерирует и не отправляет backend UUID или другой `device_id`.
Сервер использует MAC как идентификатор устройства и назначает собственный
непрозрачный ID для REST/WebSocket API. Алгоритм формирования этого ID клиенту
не нужен; сервер должен сохранять его для того же MAC при переподключении.

MAC — идентификатор, но не криптографическая аутентификация: клиент в локальной
сети может его подделать. Протокол не подтверждает подлинность устройства.

### Оборудование `onboards`

Каждый элемент содержит:

| Поле | Смысл |
|---|---|
| `name` | Тип/название оборудования, например `camera` или `thermal` |
| `url` | Адрес подключения к этому оборудованию |

Отправляйте актуальный полный список при каждом новом соединении. Если
дополнительного оборудования нет, `onboards` оставьте пустым. Backend принимает
URL с любой схемой, поэтому прошивке не нужно ограничиваться `http`/`https`:
возможны, например, `rtsp://`, `http://`, `https://` и схемы производителя.
Сервер сохраняет URL как метаданные, не подключается к нему и не проверяет
доступность. Не включайте в URL пароли или токены: поле возвращается веб-клиентам.

### Пример кадра `Syn`

Для MAC `02:11:22:33:44:55` без дополнительного оборудования protobuf-тело:

```text
0A 06 02 11 22 33 44 55
```

Полный кадр — 8 байт тела:

```text
00 00 00 08 0A 06 02 11 22 33 44 55
```

Текстовое представление Syn с оборудованием:

```text
mac: "\x02\x11\x22\x33\x44\x55"
onboards {
  name: "camera"
  url: "rtsp://192.168.1.50:554/stream"
}
onboards {
  name: "thermal"
  url: "thermal://192.168.1.50/device/0"
}
```

Для protobuf `bytes` передаются шесть байтов, а не текст, показанный в
debug-представлении.

## Ответ `Ack`

Сервер отвечает ровно одним length-prefixed сообщением `telemetry.v1.Ack`.

| `code` | Значение | Действие устройства |
|---:|---|---|
| `0` | Регистрация прошла успешно; сервер готов принимать telemetry | Начать передачу снимков |
| `1` | Регистрация отклонена | Закрыть соединение; не отправлять telemetry |

Других кодов пока нет. Если TCP разорван или ACK не получен до таймаута клиента,
считайте handshake неуспешным, закройте сокет и переподключитесь с backoff.
Некорректный framing или неразбираемый protobuf может привести к закрытию без ACK.

Из-за значений proto3 по умолчанию успешный `Ack{code: 0}` имеет пустое тело:

```text
00 00 00 00
```

Это валидный protobuf-кадр. `Ack{code: 1}` кодируется телом `08 01`:

```text
00 00 00 02 08 01
```

Не ждите от сервера дополнительных сообщений после успешного ACK.

## После ACK: `Telemetry`

После `Ack.code == 0` отправляйте кадры `telemetry.v1.Telemetry` в формате,
описанном в [`iot-device-client-tutorial.md`](iot-device-client-tutorial.md).
Каждый пакет — полный снимок, а не delta. UUID и MAC в `Telemetry` не дублируются.

- Рекомендуемая частота — около 5 снимков/с (каждые 200 мс). Отдельная прошивка
  может отправлять реже, но должна учитывать таймаут сервера.
- Сервер закрывает подключение, если не получает полный следующий кадр в течение
  настроенного таймаута (по умолчанию 5 секунд).
- Максимальный размер protobuf-тела задаётся конфигурацией backend (по умолчанию
  65 536 байт).
- Пустой `tracks` означает отсутствие целей. Отсутствующий `position` означает
  отсутствие GPS-фиксации; `(0, 0)` — допустимая координата.
- `heading_valid=true` требует присутствующего `heading_deg` в диапазоне `[0,360)`.
- Числовые значения должны удовлетворять ограничениям контракта: вероятности и
  `hit_ratio` — `[0,1]`, координаты — диапазонам WGS-84, distance/speed/HDOP неотрицательны.
- Передавайте конечные значения; `NaN`/`Infinity` не допускаются.
- `alarm_active` — состояние на момент снимка, не отдельное событие. Краткий
  переход, полностью прошедший между снимками, сервер может не увидеть.

Скалярные поля proto3 со значением `0`/`false` обычно отсутствуют в wire bytes,
но после декодирования имеют эти значения. Для `position` и `optional` полей
сохраняйте различие между отсутствием и присутствующим нулём.

## Рекомендуемый цикл клиента

```text
loop:
    socket = tcp_connect(server_host, server_port)
    if connect failed:
        wait with bounded backoff
        continue

    send_frame(socket, protobuf_encode(Syn(mac, current_onboards)))
    ack = receive_one_frame_with_timeout(socket)
    if ack cannot be decoded or ack.code != 0:
        close(socket)
        wait with bounded backoff
        continue

    while socket is connected:
        snapshot = read_current_sensor_state()
        validate snapshot locally
        send_frame(socket, protobuf_encode(Telemetry(snapshot)))
        sleep_until_next_period()

    close(socket)
    discard queued old snapshots
    reconnect and send Syn again
```

Используйте цикл полной записи и чтения: TCP не сохраняет границы вызовов
`write`/`read`. Один `read` может вернуть часть заголовка или тела, а несколько
кадров могут прийти одним сетевым блоком.

## Изменение `onboards`

Список оборудования передаётся в `Syn`, то есть при установлении соединения.
Чтобы сообщить новый список, клиенту нужно переподключиться и отправить новый
`Syn`. Отдельного сообщения обновления оборудования пока нет.

## Безопасность и ограничения

- TLS и аутентификация IoT-устройства текущим TCP listener не предоставляются;
  используйте доверенную сеть/VPN до появления согласованной защиты.
- MAC не является секретом и не доказывает подлинность клиента.
- Несколько устройств с одинаковым MAC для сервера являются одним устройством;
  новый Syn с таким MAC считается переподключением и заменяет старую сессию.
- USB-шлюз текущим backend не поддерживается.
- Переход со старой прошивки, отправляющей Telemetry первым кадром, требует
  согласованного обновления: новый сервер ожидает Syn и старый порядок не принимает.

## Проверка

После реализации handshake backend-проверка будет состоять из следующих шагов:

1. Запустить `go run ./cmd/server -config-path configs/on-premise.yaml`.
2. Подключить устройство и отправить Syn.
3. Проверить `Ack.code == 0` и появление стабильного ID в `GET /api/v1/devices`.
4. Убедиться, что `onboards` присутствуют в REST-ответе.
5. Отправить несколько Telemetry-кадров и проверить WebSocket-подписку.
6. Отключиться и переподключиться с тем же MAC: ID должен сохраниться,
   connected_at/address обновиться.

**Важно:** этот документ задаёт целевое поведение handshake. Пока TCP-сервер не
реализовал Syn/Ack и REST не добавил `onboards`, прошивка с новым алгоритмом
не совместима с текущим запущенным backend.
